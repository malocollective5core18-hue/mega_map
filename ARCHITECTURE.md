# Architecture

The customer map is served from `index.html` by Django. The vanilla JavaScript calls same-origin Django REST Framework endpoints under `/api/`. Leaflet 1.9.4 public and staff assets are pinned with Subresource Integrity. Public imagery uses Esri World Imagery.

`core` owns provider codes, verification sessions, customer submissions, consent records, service visits, demand cells and audit events. PostgreSQL is the application database. Customer phone HMACs are indexed for code-history linking; values depend on `SECRET_KEY`, so rotation requires a controlled rehash migration. Coordinates are indexed decimal latitude/longitude fields; duplicate detection uses sorted PostgreSQL transaction advisory locks and a bounding query followed by haversine distance. Public map APIs only query served, opted-in businesses and round coordinates to 0.001 degrees. Demand cells are only returned once they aggregate at least three requests. Customer location stores final coordinates, reported accuracy, source, server-calculated fix age, pin offset, manual-move flag, and optional staff-corrected coordinates; it never stores the original GPS coordinate or motion stream.

Staff use `/staff/` with Django session authentication and mandatory TOTP MFA. API permissions distinguish dispatcher, admin, service provider, superuser, and field-team roles. Field-team list/detail access is restricted to assigned records; the one-time arrival check returns distance but stores no staff location, and its audit event records only a distance band. Successful sensitive reads, staff-user listing, failed sign-in, denied staff authorization, new-customer key verification, customer profile changes, and staff edits create audit records. Audit metadata records field names/reason categories only and does not contain submitted values. Navigation URLs are composed server-side from validated coordinates only; a staff correction becomes the navigation destination and is timestamped/audited.

`stocktaking.settings.base` contains shared configuration including a broad default Tanzania bounding box, accepted fix-age/skew/accuracy limits and warning/offset thresholds. The rectangular bounds are not a definitive administrative boundary and require owner approval. `dev`, `test`, and `prod` provide environment-specific settings. Provider-code hashes, bearer-token hashes, consent IP hashes, throttling and role checks are handled server-side.

## Current boundaries

The staff dashboard currently covers sign-in, searchable/paged business listing, satellite pins, customer detail, status/assignee/notes updates, pin correction, admin CSV export, recent audit events, searchable provider-code history with revoke, public-listing consent control, MFA, and assigned field-team jobs with a one-time arrival-distance check. Browser and mobile viewport behavior remains unverified unless covered by the checked-in journey suite. Render deployment configuration is in `render.yaml` and `build.sh`; see `DEPLOY.md` for setup and current free-tier limits.
